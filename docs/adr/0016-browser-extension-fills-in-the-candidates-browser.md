# 0016. The browser extension fills a form in the Candidate's own browser, and never submits it

Date: 2026-11-13
Status: Accepted for a side-loaded first version.

## Context

Automatic submission runs the employer's form in a clean Chromium inside Docker (ADR 0008). That browser has none of the Candidate's sessions, cannot pass a CAPTCHA, and has to identify the submit control from the page alone. When it cannot, the Application blocks with `automation_incomplete` and the Candidate applies by hand. The ClickHouse sample of 13 Nov 2026 is exactly that: `blocked_detail` "couldn't find exactly one submit button", no click, and the failure held no more information than that sentence.

The Candidate's own browser has the missing pieces: the employer session, the human who can solve a CAPTCHA, and a person who can see which button submits. Autofill extensions in this market work for the same reason. Eve already owns the part those extensions lack: the approved answers, the salary and work-context rules, and the prepared documents.

## Decision

- A Chrome/Edge MV3 extension, side-loaded, lives in `apps/extension`. It is a **fill assistant**: it reads the employer form in the Candidate's tab, asks Eve for the values, fills them, and highlights the fields Eve cannot answer. The Candidate clicks Submit. The extension never clicks Submit or a link; it may click a checkbox or radio to set it the way the Candidate would.
- It does not solve CAPTCHAs, sign in, create accounts, or read LinkedIn. It acts only on the tab the Candidate invokes it on, after a click.
- **Authentication is the Eve session, not an extension token.** The extension keeps no credential. On fill it finds an open Eve tab (or opens one), and a content script there calls `GET /v1/session` for the CSRF token and `POST /v1/extension/fill` with the session cookie. Signing out of Eve disconnects the extension. There is nothing to rotate or leak from `chrome.storage`.
- **One new endpoint**, `POST /v1/extension/fill`, behind the normal session and CSRF guards. Body: `{ url, fields: [{ ref, label, kind, required, options?, combobox? }] }`. Response: `{ application: { id, company, roleTitle } | null, values: [{ ref, value, kind }], documents: [{ ref, document }], unanswered: [{ ref, label, detail }] }`, where `kind` is the control kind the extension read, repeated back so the filler does not guess it, and `document` is `resume` or `cover_letter`. It calls the same `loadAnswerSources` the automatic path calls, writes nothing, and records no attempt, so it carries no `@ConvertedFeature` gate: a draft Candidate can fill a form. Field labels are treated as untrusted text and capped. A document answer is named in `documents` by its ref and kind, never in `values`, and no document bytes cross this endpoint.
- **The Candidate reviews before anything is typed.** The extension's flow has two clicks. The first reads the page and asks Eve, and fills nothing: the popup lists every page label next to the value that would be typed, plus the fields Eve cannot answer, and masks values whose label looks sensitive (gender, sex, sexual orientation, pronouns, race, ethnicity, Hispanic/Latino, religion, disability, veteran, citizenship, criminal history, social security, salary, date of birth, sponsorship, visa, age) with a `sensitive` mark while still listing them. Only the second click, **Fill these values**, sends the refs of that reviewed plan (the whole plan; slice 1 has no per-row selection) and the background fills exactly those refs from the plan it stored for that tab and URL. A plan is one-shot and is held in `chrome.storage.session` (memory only, removed after the fill), and a page that changed between the clicks is refused rather than filled.
- **The employer page and its third-party scripts can read every value that is filled.** A value typed into the page is in the page's DOM, and scripts on that page can read it. The extension cannot prevent that, so the review step is the Candidate's control: they see what will be typed, and a sensitive-looking value is masked there. Nothing is filled on the first click.
- **Only a visually visible control is fillable.** A control, or the label element that names it, must be genuinely visible: `checkVisibility({ checkOpacity: true, checkVisibilityCSS: true })` where the browser has it, an opacity not below 0.1, no screen-reader-only clip pattern, and a bounding box of at least 4x4 inside the box that scrolls it (the outermost scrolling container inside the page, or the document when the window scrolls). A field below the fold is still fillable, and so is a field inside an inner container's scroll box; only a box pushed outside the page, or a scroll box that itself sits outside the page, is refused. A visually hidden native radio or checkbox inside a visible label stays fillable, because a custom control draws its own mark; a hidden text input with a visible label is not, so a page cannot harvest an answer through a control the Candidate cannot see. A file input is the exception the custom uploader forces: its native box is hidden by design, so it is read when its own box is visible, or when the nearest field container around it (at most three ancestors up, holding exactly one file input) is visible and carries text the Candidate can read. It is never clicked and no file chooser is opened.
- **Refs live only in the injected script's closure.** `read()` builds a fresh `ref` -> element map and `fill()` resolves refs from that map alone. No ref is written into the DOM, so a page that forges `data-eve-ref` receives nothing, and a re-read replaces the map and drops every old ref.
- **Matching** normalises the page URL the same way the stored `application_url` was normalised, then matches an exact normalised URL, then the ATS identity the URL names (system, board and job ID), and only then a unique host-plus-path Application whose stored URL has no query. The fallback compares the port as well as the host, and a stored URL with a non-empty query is never matched by the fallback. Only an Application that can still be applied to is matched: `state = documents_ready` and `submission_state` null or `blocked`. A `queued` Application is excluded on purpose: the automatic worker could submit it while the Candidate fills it by hand. A confirmed, manual, declined, not_submitted or uncertain Application answers no match. No match, or an ambiguous one, returns `application: null` and the extension says this page is not an Eve Application; it does not guess.
- **Values are the same values automation would set.** Every field is visited, so a hard block (a required question with no Approved Answer) never stops the fields after it: the fill returns what it can and lists each block and leftover under `unanswered` with its reason, so the Candidate can answer in Eve or on the page.
- **The endpoint is throttled per Candidate** at 30 requests a minute in a fixed window, keyed by Candidate id, answering 429 with a retry hint. The counter is in one api process, not distributed: with several api processes a Candidate gets one window per process. That is deliberate for slice 1.
- **Outcome recording reuses `POST /v1/applications/:id/manual-complete`** after the Candidate confirms on the confirmation page. No new write path and no new submission state. This slice does not wire that call; recording a completed application stays in the manual-complete route and is a later slice.
- **Permissions are narrow**: `activeTab`, `scripting`, `storage`, and an optional host permission the Candidate grants once for their own Eve origin. No `<all_urls>` at install, no content script on every page. The popup accepts an `https://` Eve origin, and `http://` only for `localhost` or `127.0.0.1`.
- **Documents are attached after the second click, and only the ones reviewed.** A file input that asks for a resume or cover letter appears in the plan as `documents: [{ ref, document }]`; the first click downloads nothing. On the second click the background downloads exactly the approved refs through the Eve tab from `GET /v1/applications/:id/documents/resume.pdf` or `cover-letter.pdf`, turns the bytes into a `File` and a `DataTransfer` file list, assigns it to the input and raises `input` and `change` as a real selection would. The result is read back by file name. No file chooser opens, no click is sent to the input, and only the prepared PDFs are ever attached: no other file from disk and no DOCX. A download that fails (signed out, no prepared PDF, over 10 MB, or a closed Eve tab) is reported as one unattached document with its reason and never stops the scalar fill. Ashby's "Autofill from resume" uploader is skipped; the two document uploaders are the only ones verified.

## Alternatives rejected

- **A long-lived extension token.** It buys nothing here: the Eve tab already holds a session, and a token would be a second credential to store, rotate and revoke, in an extension that otherwise keeps no secrets.
- **Giving the server-side browser stored employer credentials.** That is the failure it already has, moved to a worse place: passwords for third-party sites saved in Eve.
- **Auto-submit from the extension.** It removes the human check that currently guarantees nothing is sent without approval, and it takes on the same ToS exposure as crawling.
- **Reading LinkedIn from the extension.** Separate product decision; capturing a post the Candidate is already viewing is not the same as reading the site.

## Consequences

- A fill needs an Eve tab in the same browser profile. The extension opens one when there is none, which is visible and slightly slower.
- A fill calls Eve with the session cookie, so it counts as activity and extends the Eve session's idle timeout. Signing out still disconnects the extension immediately.
- Matching is limited to Applications that can still be applied to. A Candidate who fills a confirmed or declined Application gets no match and fills by hand; that is deliberate, because a fill must not attach an answer or a later manual-complete to an application that is already settled.
- Outcome recording is not wired in this slice: the extension fills and the Candidate submits, but no manual-complete call follows, so the Application's state does not change.
- The automatic path and the extension share the answer rules but not the page reader. The extension reads labels with its own copy of the rules; the server still classifies every label and refuses what it cannot place, so a reader drift shows up as `unanswered`, not as wrong data.
- The extension is unpacked, so updates are manual and there is no store review. A published build is a later decision.
- Every filled page is a page the Candidate invoked the extension on. Nothing runs in the background on a timer.
- The employer's page and its third-party scripts can read an attached PDF exactly as they could a file the Candidate chose by hand, and many ATS upload a selected file as soon as the input changes. That is why the review click downloads nothing: the second click is the approval, and the popup says so before the file leaves the browser.
- Only the prepared resume and cover letter are attached, and only as PDFs; a form that asks for DOCX or another format is left to the Candidate.
- Document attachment is verified against Ashby's two uploaders only. Other ATS uploaders are read and attached best-effort, and an uploader whose container or label the reader cannot place is left for the Candidate rather than guessed at.
